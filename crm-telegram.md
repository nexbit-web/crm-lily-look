# Telegram-бот: что нужно сделать на стороне CRM

Документ для разработчика CRM. Описывает всё, что требуется добавить в CRM, чтобы работать с Telegram-ботом менеджеров LILY LOOK.

Сайт и CRM живут в одной базе Postgres (Neon). Бот — часть сайта: он крутится на хостинге сайта, принимает вебхуки от Telegram и пишет в ту же базу. Никаких HTTP-вызовов между CRM и ботом нет и не нужно — **весь обмен идёт через базу**.

## Что уже сделано, а что нет

Таблицы `BotUser`, `BotInvite`, `OrderEvent`, `BotNotice`, `BotUpdate` и тип `BotRole` **уже созданы в боевой базе**. Миграции применять не нужно, схему менять не нужно. CRM работает с готовыми таблицами.

Со стороны CRM нужно добавить три вещи:

1. экран выдачи кодов доступа (`BotInvite`);
2. экран управления доступом (`BotUser`);
3. правило: **каждая смена `Order.status` из CRM пишет строку в `OrderEvent`**, а отмена вдобавок возвращает товар на склад.

Третий пункт — обязательный. Первые два можно делать в любом порядке.

## Модель данных

Пять таблиц. Колонка «кто пишет» — самое важное в этой таблице.

| Таблица      | Назначение                            | Пишет CRM        | Пишет бот         |
| ------------ | ------------------------------------- | ---------------- | ----------------- |
| `BotInvite`  | одноразовые коды доступа              | да, создаёт      | гасит (`usedAt`)  |
| `BotUser`    | человек, у которого есть доступ       | `isActive`, роль | создаёт при входе |
| `OrderEvent` | история смены статусов                | **обязательно**  | при каждой смене  |
| `BotNotice`  | id отправленных в Telegram сообщений  | **не трогать**   | служебная         |
| `BotUpdate`  | защита от повторной обработки события | **не трогать**   | служебная         |

`BotNotice` и `BotUpdate` — внутренняя кухня бота. Читать их можно, писать в них нельзя: `BotNotice` хранит ссылки на конкретные сообщения в Telegram, `BotUpdate` — дедупликацию апдейтов. Ручная правка ломает и то, и другое.

### Общие правила для всех таблиц

- `id` — `text`, **без дефолта в базе** (Prisma генерирует cuid в приложении). CRM должна подставлять id сама: `gen_random_uuid()::text` подходит.
- Время — `timestamp without time zone`, везде **UTC**. Пишите `(now() AT TIME ZONE 'utc')`, читайте как UTC и переводите в Киев только на экране.
- `telegramId` и `chatId` — `bigint`. В JS читайте как строку или `BigInt`: Telegram id уже вплотную подходят к пределу `Number`.
- Колонки `updatedAt` Prisma обновляет в приложении, а не триггером. Если CRM правит строку сырым SQL — ставьте `"updatedAt" = (now() AT TIME ZONE 'utc')` сами, иначе поле застынет. Колонка есть не везде: у `Order` и `BotUser` она есть, у `ProductVariant`, `OrderEvent` и `BotInvite` — нет.

## 1. Экран «Коды доступа»

Telegram id человека заранее знать не нужно — он приносит его сам. CRM создаёт код, человек отправляет боту `/start КОД`, и **только в этот момент** появляется строка в `BotUser`.

### Таблица `BotInvite`

| Колонка     | Тип         | Смысл                                           |
| ----------- | ----------- | ----------------------------------------------- |
| `id`        | text        | генерирует CRM                                  |
| `code`      | text UNIQUE | то, что человек отправит боту                   |
| `role`      | BotRole     | `ADMIN` · `MANAGER` · `COURIER`                 |
| `note`      | text NULL   | кому выдан — только для глаз владельца          |
| `expiresAt` | ts NULL     | `NULL` = бессрочный                             |
| `usedAt`    | ts NULL     | **заполняет бот**. `NULL` = код ещё живой       |
| `usedById`  | text NULL   | **заполняет бот**: `BotUser.id` того, кто вошёл |
| `createdAt` | ts          | `now()`                                         |

### Требования к самому коду

Бот сравнивает код **точно, посимвольно**: ни регистр, ни пробелы внутри он не нормализует. Отсюда три требования:

- генерируйте **в верхнем регистре**, без пробелов;
- используйте алфавит без похожих символов, чтобы код можно было продиктовать по телефону: `23456789ABCDEFGHJKLMNPQRSTUVWXYZ` (нет `0`, `O`, `1`, `I`);
- формат, к которому привык владелец: `LILY-` + 6 символов, например `LILY-7K2M4P`. Это соглашение, а не проверка — бот примет любую строку.

Длина в 6 символов из 32-символьного алфавита — это миллиард вариантов. Плюс бот сам блокирует перебор: 5 неверных попыток подряд с одного Telegram id — и десять минут тишины.

### Создать код

```sql
INSERT INTO "BotInvite" (id, code, role, note, "expiresAt", "createdAt")
VALUES (
  gen_random_uuid()::text,
  'LILY-7K2M4P',
  'MANAGER',
  'Олена, склад',
  (now() AT TIME ZONE 'utc') + interval '7 days',  -- или NULL, если бессрочно
  (now() AT TIME ZONE 'utc')
);
```

У `code` уникальный индекс. При коллизии (шанс мизерный, но обработать надо) генерируйте новый и повторяйте, а не показывайте пользователю ошибку базы.

### Показать список кодов

```sql
SELECT i.code, i.role, i.note, i."createdAt", i."expiresAt", i."usedAt",
       u.name AS used_by_name, u.username AS used_by_username
FROM "BotInvite" i
LEFT JOIN "BotUser" u ON u.id = i."usedById"
ORDER BY i."createdAt" DESC;
```

Состояние кода на экране считается так:

- `usedAt IS NOT NULL` — **использован**, показывайте, кем именно;
- `expiresAt < now()` — **просрочен**;
- иначе — **ждёт**, и вот его стоит показать крупно, с кнопкой «скопировать».

### Отозвать невыданный код

Удалять не обязательно, достаточно погасить — так в списке останется след:

```sql
UPDATE "BotInvite"
   SET "usedAt" = (now() AT TIME ZONE 'utc')
 WHERE id = $1 AND "usedAt" IS NULL;
```

### Что показать рядом с кодом

Человеку нужно отправить боту ровно одну строку:

```
/start LILY-7K2M4P
```

Имеет смысл выводить её целиком, готовой к копированию, — а не один код.

## 2. Экран «Доступ к боту»

### Таблица `BotUser`

| Колонка      | Тип           | Смысл                                         |
| ------------ | ------------- | --------------------------------------------- |
| `id`         | text          | создаёт бот                                   |
| `telegramId` | bigint UNIQUE | id в Telegram, приходит в подписанном вебхуке |
| `chatId`     | bigint        | личный чат — туда падают заказы               |
| `name`       | text          | имя из Telegram на момент привязки            |
| `username`   | text NULL     | `@username`, если он есть                     |
| `role`       | BotRole       | `ADMIN` · `MANAGER` · `COURIER`               |
| `isActive`   | boolean       | **выключатель из CRM**                        |
| `leftAt`     | ts NULL       | человек вышел сам, командой в боте            |

Строки здесь создаёт только бот. CRM меняет `isActive` и `role`.

### Кто сейчас с доступом

Доступ действует, когда `isActive = true` **и** `leftAt IS NULL`. Это ровно то условие, по которому бот пускает к данным:

```sql
SELECT "telegramId", name, username, role, "isActive", "leftAt", "createdAt"
FROM "BotUser"
ORDER BY ("isActive" AND "leftAt" IS NULL) DESC, "createdAt";
```

Три состояния на экране:

| `isActive` | `leftAt` | Что показать       | Как вернуть                     |
| ---------- | -------- | ------------------ | ------------------------------- |
| true       | NULL     | **работает**       | —                               |
| false      | NULL     | **доступ отозван** | `isActive = true`               |
| false      | не NULL  | **вышел сам**      | новый код, либо снять обе метки |

### Отозвать доступ

```sql
UPDATE "BotUser" SET "isActive" = false, "updatedAt" = (now() AT TIME ZONE 'utc')
 WHERE "telegramId" = $1;
```

Действует с первого же касания: бот проверяет доступ на каждое сообщение и каждое нажатие кнопки, ничего не кэшируя. Отозванный не получит ни новых заказов, ни ответа на команду.

**Отозванному новый код не поможет** — и это сделано намеренно. Строка в `BotUser` остаётся, повторная привязка того же Telegram id запрещена, иначе отзыв обходился бы выдачей нового кода. Чтобы вернуть человека, снимайте отзыв, а не выдавайте код.

### Вернуть доступ

```sql
-- Отозванному владельцем:
UPDATE "BotUser" SET "isActive" = true, "updatedAt" = (now() AT TIME ZONE 'utc')
 WHERE "telegramId" = $1;

-- Тому, кто вышел сам: одного isActive МАЛО, нужно снять и leftAt.
UPDATE "BotUser"
   SET "isActive" = true, "leftAt" = NULL, "updatedAt" = (now() AT TIME ZONE 'utc')
 WHERE "telegramId" = $1;
```

Это самая частая ошибка на этом экране: человек вышел сам, ему включили `isActive`, а бот всё равно его не пускает — потому что `leftAt` остался. Проще всего выдать такому человеку новый код: бот сам приведёт строку в порядок, сохранив историю его действий.

### Чего делать нельзя

**Не удаляйте строки `BotUser`.** На них ссылается `OrderEvent.actorId`; при удалении ссылка обнулится, и в истории заказов вместо имени менеджера навсегда останется «CRM». Выключайте через `isActive`.

### Роли

| Роль      | Что может в боте                                      |
| --------- | ----------------------------------------------------- |
| `ADMIN`   | всё, что менеджер, плюс отчёты и выдача кодов из бота |
| `MANAGER` | весь маршрут заказа, включая отмену                   |
| `COURIER` | только «Отримано», и только у отправленного заказа    |

Роль можно поменять в `BotUser.role` — изменение подхватится на следующем действии человека. Меню команд в Telegram при этом обновится не сразу: оно переустанавливается, когда человек отправит боту `/start` или `/dopomoha`.

**Следите, чтобы `ADMIN` с доступом был не один.** Коды выдаются только админом и только изнутри бота, так что если единственный админ потеряет доступ, выдать новый код будет некому — останется только вставить строку в `BotInvite` руками. Бот предупреждает последнего админа при выходе, но от отзыва доступа через CRM такой защиты нет: **не выключайте последнего активного `ADMIN`**, а если выключаете — сначала заведите второго.

## 3. Обязательное: смена статуса из CRM

Статус заказа может менять и бот, и CRM. Чтобы они не расходились, CRM должна соблюдать три правила.

### Правило 1. Каждая смена статуса пишет `OrderEvent`

`Order.status` — это текущий срез, `OrderEvent` — история. Бот берёт из истории подпись «кто и когда изменил» и показывает её в карточке заказа. Если CRM меняет статус молча, история становится дырявой, а в карточке пропадает подпись.

| Колонка     | Значение при записи из CRM                        |
| ----------- | ------------------------------------------------- |
| `orderId`   | `Order.id`                                        |
| `status`    | новый статус                                      |
| `actorId`   | **`NULL`** — так помечается «изменено не из бота» |
| `note`      | необязательно: причина, номер накладной и т.п.    |
| `createdAt` | `now()` в UTC                                     |

`actorId = NULL` бот показывает как «CRM». Не выдумывайте для CRM фиктивного `BotUser` — `NULL` и есть правильное значение.

### Правило 2. Меняйте статус с условием

Бот меняет статус условным `UPDATE ... WHERE status = <ожидаемый>`, чтобы двое не перетёрли друг друга. CRM должна делать так же: если между чтением и записью статус успел измениться, обновление не должно произойти молча.

### Правило 3. Отмена возвращает товар на склад

Остатки списываются в момент оформления заказа. Если при отмене их не вернуть, отменённый заказ тихо съест склад. Бот возвращает остатки сам, в той же транзакции; **при отмене из CRM это должна сделать CRM**.

### Готовый запрос: отмена из CRM

```sql
BEGIN;

-- 1. Статус — только если он ещё не отменён.
UPDATE "Order"
   SET status = 'CANCELLED', "updatedAt" = (now() AT TIME ZONE 'utc')
 WHERE id = $1 AND status <> 'CANCELLED';
-- 0 строк — заказ уже отменён: ROLLBACK, дальше не идём.
-- Иначе остатки вернутся дважды.

-- 2. Вернуть остатки. Позиции без variantId пропускаются: вариант могли
--    удалить из каталога уже после заказа, возвращать некуда.
--    Суммируем заранее: если один вариант попал в заказ двумя строками,
--    UPDATE ... FROM без группировки применил бы только одну из них.
UPDATE "ProductVariant" v
   SET stock = v.stock + r.qty
  FROM (
    SELECT "variantId", sum(quantity) AS qty
      FROM "OrderItem"
     WHERE "orderId" = $1 AND "variantId" IS NOT NULL
     GROUP BY "variantId"
  ) r
 WHERE v.id = r."variantId";

-- 3. Запись в историю.
INSERT INTO "OrderEvent" (id, "orderId", status, "actorId", note, "createdAt")
VALUES (gen_random_uuid()::text, $1, 'CANCELLED', NULL, 'Скасовано в CRM',
        (now() AT TIME ZONE 'utc'));

COMMIT;
```

### Готовый запрос: любой другой статус

```sql
BEGIN;

UPDATE "Order"
   SET status = $2, "updatedAt" = (now() AT TIME ZONE 'utc')
 WHERE id = $1 AND status = $3;   -- $3 — статус, который CRM видела
-- 0 строк — кто-то изменил раньше: ROLLBACK и перечитать заказ.

INSERT INTO "OrderEvent" (id, "orderId", status, "actorId", "createdAt")
VALUES (gen_random_uuid()::text, $1, $2, NULL, (now() AT TIME ZONE 'utc'));

COMMIT;
```

### Какие переходы допустимы

Бот ходит по маршруту:

```
NEW ──> CONFIRMED ──> SHIPPED ──> DELIVERED
 └──────────── CANCELLED ───────────┘
```

База этот маршрут **не проверяет** — CRM технически может поставить любой статус, включая откат назад. Бот это переживёт: при следующем нажатии карточка в Telegram перерисуется под фактический статус. Но менеджер увидит скачок состояния, которого не делал, поэтому без нужды назад не откатывайте.

### Что произойдёт в Telegram после правки из CRM

Ничего — до первого касания. Сообщения в чатах показывают то состояние, которое было на момент отправки; бот не рассылает обновления при каждой правке в базе, иначе пришлось бы непрерывно её опрашивать. Как только менеджер нажмёт любую кнопку под таким сообщением, карточка перерисуется под настоящий статус и покажет актуальные кнопки. Сам статус от этого промаха не изменится.

Из этого следует: **если статус меняется в CRM, менеджеру в Telegram об этом никто не скажет.** Если это важно для процесса — сообщайте сами, вне бота.

## 4. Экран истории заказа (необязательно, но полезно)

```sql
SELECT e.status, e."createdAt", e.note,
       COALESCE(u.name, 'CRM') AS actor,
       u.role AS actor_role
FROM "OrderEvent" e
LEFT JOIN "BotUser" u ON u.id = e."actorId"
WHERE e."orderId" = $1
ORDER BY e."createdAt";
```

Здесь видно, кто из менеджеров вёл заказ и сколько времени он простоял в каждом состоянии. `actorId IS NULL` — это CRM или сам сайт.

Отдельно полезный отчёт — кто сколько заказов провёл:

```sql
SELECT u.name, u.role, count(*) AS moves
FROM "OrderEvent" e
JOIN "BotUser" u ON u.id = e."actorId"
WHERE e."createdAt" >= (now() AT TIME ZONE 'utc') - interval '30 days'
GROUP BY u.name, u.role
ORDER BY moves DESC;
```

## 5. Чего в CRM делать не нужно

- **Не отправлять ничего в Telegram.** Рассылку заказов и перерисовку карточек делает сайт. У CRM нет и не должно быть токена бота.
- **Не трогать `BotNotice` и `BotUpdate`.**
- **Не удалять `BotUser`** — выключать через `isActive`.
- **Не заполнять `BotInvite.usedAt` / `usedById` при выдаче** — это делает бот в момент входа. CRM пишет `usedAt`, только когда отзывает невыданный код.
- **Не создавать `BotUser` вручную.** Строка появляется при входе по коду: только в этот момент известны `telegramId` и `chatId`, а подделать их нельзя.
- **Не заводить фиктивного `BotUser` для CRM** — для этого есть `actorId = NULL`.

## Чеклист внедрения

- [ ] Экран «Доступ»: список `BotUser`, три состояния, смена роли, отзыв и возврат доступа (**с очисткой `leftAt`**), запрет на выключение последнего активного `ADMIN`.
- [ ] Каждая смена `Order.status` из CRM пишет `OrderEvent` с `actorId = NULL`.
- [ ] Отмена заказа из CRM возвращает остатки в той же транзакции.
- [ ] Все `UPDATE "Order"` идут с условием по ожидаемому статусу.
- [ ] Время пишется в UTC, `id` генерируется CRM, `bigint` читается не как `Number`.
- [ ] (по желанию) История заказа из `OrderEvent` на карточке заказа.
